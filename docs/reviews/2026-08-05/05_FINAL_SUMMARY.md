## Headline

Two of PrettyChat's shipped default format strings asked Blizzard's chat code for arguments it never
passes, so every generic reputation loss and every guardian-experience gain raised a Lua error inside
Blizzard's own handler and dropped the message. The automated case that was supposed to catch exactly
this validated each format string against arguments it synthesized *from that same string* — a check
that cannot fail — so both defects shipped in 1.4.0 under a green suite. This cycle fixes the two
defaults, replaces the tautological case with one that compares each override against the Blizzard
string it replaces, points the settings panel's read-only **Original** box at the addon's own live
per-client snapshot instead of a shipped English reference dump (it was showing English formats on
German and French clients), and moves four settings strings into the localization manifest they were
already claimed to be in.

## Changes by theme

### Theme A — the defaults table agrees with the strings it replaces

**What changed.** `Reputation.FACTION_STANDING_DECREASED_GENERIC` no longer asks for an amount that
Blizzard's one-argument message does not carry, and
`Reputation.FACTION_STANDING_INCREASED_GUARDIAN` no longer puts a numeric conversion where the client
passes the guardian's name. A new headless case now compares every default's conversion sequence
against the corresponding entry in the addon's own `NS.GlobalStrings` reference — position by
position, string-vs-number — and allows the safe direction (dropping trailing conversions, which four
existing defaults do on purpose) while rejecting the unsafe one.

**Why it mattered.** These are not cosmetic. `string.format` raises when a conversion has no argument
or the wrong type, and the raise happens inside Blizzard's chat handler on the addon's behalf: the
user sees a red error and loses the message entirely. Both defaults are on by default. The old case
made the data look guarded when nothing was checking it against reality.

**Findings covered:** F-001, F-002, F-003. **Changes implemented:** C-01, C-02.

**Files touched:**

* `defaults/Defaults.lua`
* `tests/test_defaults.lua`
* `docs/test-cases.md` *(regenerated)*
* `README.md` *(test badge)*

### Theme B — one source of truth for "the Blizzard original"

**What changed.** The settings panel's read-only **Original** box now reads
`PrettyChat.originalStrings` — the snapshot the addon takes from `_G` at `OnEnable`, before it
overwrites anything — falling back to the shipped `NS.GlobalStrings` dump and then to
`(original not available)`. `/pc test` already read the snapshot; the two surfaces now agree.

**Why it mattered.** The dump is an enUS reference regenerated by hand after a client patch. On a
German or French client the panel showed the English original beside a German chat line, and on any
client it could show a format Blizzard had since changed. The snapshot covers exactly the keys the
panel draws, so the less accurate source was never the necessary one.

**Findings covered:** F-004. **Changes implemented:** C-03.

**Files touched:**

* `settings/Panel.lua`
* `tests/test_panel.lua`
* `docs/global-strings.md`

### Theme C — the translatable surface matches what the manifest claims

**What changed.** Four user-visible settings strings — the per-category `Enable <Category>` label and
its tooltip, the **Defaults** button tooltip, and the cross-registration warning on a shared Blizzard
global — are now `L` format strings with the category interpolated, and are listed in
`locales/enUS.lua`'s seeded manifest.

**Why it mattered.** `locales/enUS.lua` presents its block as the authoritative manifest of the
addon's user-facing string surface. That was true of every string already wrapped in `L[...]` and
false of these four, which were assembled by concatenation and could never reach a translator — and
whose English word order was baked into the concatenation.

**Findings covered:** F-006. **Changes implemented:** C-04.

**Files touched:**

* `settings/Schema.lua`
* `settings/Panel.lua`
* `locales/enUS.lua`

### Theme D — small correctness and honesty repairs

**What changed.** `LandingRows` is called as the method the library declares it as rather than through
a dot that worked only because the body ignored `self`; two `gsub` results are parenthesized so the
replacement count stops riding along as a second argument to `SetText`; and the Options degradation
stub's comment now names the guard that actually makes its omitted layout constants unreachable (the
`EnsureScroll` early return) instead of claiming a stronger invariant than the code has.

**Why it mattered.** None of the three misbehaves today. All three describe the code inaccurately, and
the first two are one library change or one refactor away from a `nil` index.

**Findings covered:** F-008, F-009, F-010. **Changes implemented:** C-05.

**Files touched:**

* `settings/Panel.lua`
* `settings/OptionsSetup.lua`

## SavedVariables / migration notes

**No schema bump.** `Database.SCHEMA_VERSION` stays at `1` and `core/Database.lua`'s `migrations`
table stays empty. The stored *shape* is untouched; only two `default` values moved, and defaults do
not live in SavedVariables.

**One consequence worth stating plainly.** `Schema.Set` auto-clears a stored value that equals the
row's default (`settings/Schema.lua:111-115`). A user who had previously typed the old (broken)
default back in — or whose stored value happened to equal it — now holds it as an **explicit
override**, and will keep seeing the error until they clear it. Existing profiles otherwise
auto-migrate with no action.

**Recovery, for the release notes:** that string's **Reset** button on its settings page, or
`/pc reset Reputation.FACTION_STANDING_DECREASED_GENERIC.format`. A full `/pc resetall` is not
required.
